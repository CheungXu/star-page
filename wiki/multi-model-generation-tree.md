# 多模型并行生成与生成树（会话=树，Node=Page）

面向"一次请求并行多个模型、可对比、可多轮迭代、可分支"的生成式产品，记录一套兼顾当前需求与未来扩展的数据/交互结构。

## 三层结构

- 会话（conversation）= 生成树上的一条线：一次"创作"在多轮迭代中始终是一棵树；从更早一轮分叉时另起一条会话，用分叉指针接回原会话（见下文「分叉」）。
- 批次（batch）= 一轮生成：持有该轮共享数据（prompt、文件、抽取文本、选中模型）与树关系（基点 `base_page_id`、类型 `kind`、合并来源 `source_page_ids`）。
- 节点（node）= 某个模型的一个结果：直接映射为可独立分享的 `Page`（复用既有 `/p/{page_id}` 访问网关），各自有产物版本与 token 记录。

一轮内每个模型一个节点（兄弟节点共享同一个 `parent`）。"续写"永远单父，所以会话内是一棵严格的树，便于索引与导航。

## 为什么 Node = Page

- 每个模型结果天生需要独立可分享链接（用户可能更想要其中某个、或在不同阶段/不同受众用不同结果）。
- 复用既有页面访问网关与"固定视口缩放"预览，serving 不改。
- 老数据等价于"单节点单批次会话"，迁移成本低。

对比："一个 Page 多个候选版本"在分支/多轮场景下，版本号线性语义与分支会冲突，serving/权限改动更大，不推荐。

## 合并：另起新会话，而不是把会话变成 DAG

多个节点融合时，如果留在同一会话里就会形成多父 DAG，会话越大越难索引、用户越容易混乱。更好的做法：

- 合并 = 新建一个会话，其根批次 `kind=merge_seed` + `source_page_ids=[跨会话节点...]` 记录血缘。
- 每个会话始终是一棵干净的树；会话之间用 merge 边形成更高层的松散关系，复杂度被限制在"会话内是树"。

## 分叉：从更早一轮继续 = 另起一条会话（底层仍是一棵树）

如果允许从任意旧节点继续、又把所有轮次按时间铺在一条对话里，分叉一多，"第几轮"（时间）和"基于谁"（树关系）就混在一起，用户得自己在脑子里拼树。更好的呈现：**每条会话在界面上永远是一条直线，分叉即新会话**。

- **何时分叉**：只看基点位置，不看换没换模型。基点在当前会话最后一轮 = 线性续写，留在原会话；基点在更早的轮次 = 分叉。前后端用同一条规则判断，后端为准。
- **继承而不复制**：新会话只记三根指针（来源会话、继承到哪一轮、选中的节点）。分叉点及之前的轮次运行时沿指针拼出来，节点和产物不复制；节点的 `parent_page_id` 允许跨会话，所以"沿父链收集上下文"的生成逻辑一行不用改，天然只带这条分支的历史。
- **指针指向真正的主人**：在分叉会话里选"继承来的那一轮"再分叉时，指针越过中间会话直接指回拥有那一轮的会话。这样任何会话的历史都是"沿指针往上、每段截一个前缀"拼出来，链路单一，不会出现绕路或环。
- **呈现**：继承的轮次照常完整显示（含当轮所有模型结果，被选中的高亮），在最后一个继承轮次下放一条分界"以上 N 轮来自《原会话》· 查看原会话"；新轮次编号接着往下数。侧边栏分叉会话与普通会话平级，带"分叉自 X · 第 N 轮"标签。
- **何时真正建会话**：提交新需求时才建；只点选基点不提交不产生空会话。
- **删除要算引用**：删原会话时，被未删除分支继承的那段前缀不能删（否则分叉会话的历史断掉）；页面链接是否有效应只看节点自己的删除标记，不再看所属会话。最后一个继承者被删时，再沿链往上把已删来源里不再被引用的节点一并清掉。
- **并行续写只看最近一轮**：不选基点时，所有模型都从当前会话视图的最近一轮接着改。参与了最近一轮且已完成的模型接自己那一版；新加入、上一轮没选、上一轮失败的模型接最近一轮第一个完成的结果。不要按"每个模型在整棵树里自己最新的节点"去找：会串到别的分支，也会让上一轮没选的模型跳回更早那版、丢掉上一轮的修改，更不能让新模型从零生成。这样每轮可以自由换模型，用户感知始终是"在当前页面上接着改"。

对比"一棵树一个会话、内部加分支表"：语义更纯，但历史列表、收藏、删除、搜索、分享都要从按会话改成按分支，改动面大；"分支即会话 + 分叉指针"让这些能力原样复用，代价是会话数会变多，统计时要区分"树"和"分支"。

## 并行请求与进度展示

- **生成不能挂在浏览器连接上**。每个模型 run 是一个独立任务，由服务端后台执行器跑完；浏览器只订阅事件。早期让「第一次打开事件流」触发模型调用，用户一切会话、刷新或新建对话，连接一断模型调用就被取消，状态还写不进库，任务永远停在「生成中」（2026-11-11 一晚卡住 28 路）。
- **一轮一条事件流**：前端每轮只开一条 SSE，服务端把这一轮各 run 的事件合在一起发，payload 带 `task_id`，前端按它分发。不要每个 run 开一条：HTTP/1.1 同源只有 6 条连接，第 7 个模型起就排队，同域的预览 iframe 也占名额。站点开 HTTP/2 能缓解，但 IP 直连的 80 端口仍是 HTTP/1.1。
- **可续传**：事件落库，事件流按游标从库里读；断线后带最后的游标重连，回到会话时从头回放再跟进实时进度。具体做法（每任务一个游标、终态与收尾事件同事务、非 200 后手动重连等）见 `sse-background-job-streaming.md`。
- **每人有并发上限**：每个用户同时生成的模型数有上限（默认 10，可按用户或会员放宽），超出的按提交顺序排队，界面显示「排队中」并写明原因；全站另有总上限。一轮选的模型多于剩余名额时，多出的那几个排队，前面完成一个补一个。
- **停止是显式动作**：离开页面不再等于取消，所以要给「停止生成」按钮。已完成的 run 保留并计费。被停的记为 `cancelled`：还没吐出足够内容，或上游报错时，预留原路退回；已经吐出超过起扣线后由用户主动停止，按已发生的原始成本保底收费，避免卡在收尾前白嫖。界面只显示「已停止」，不按失败样式，也不在按钮旁写收费说明，规则放在充值协议里。
- **重启自愈**：进程退出时不改任务状态，下次启动扫尾：近期中断的从头重跑一次（前端收到 `restarted` 清空旧进度），太久以前的或已经重跑过的标失败。
- 左侧每轮收成一个轻量的「进度回复气泡」（默认一行摘要，展开为各模型阶段、tokens、用时、积分的明细表），避免 N 份长步骤条堆叠；右侧 1-2 个模型并排对比，3 个以上采用「大舞台 + 缩略条 + 全屏轮播」。
- 批次状态由兄弟 run 聚合：未完成=running，全成功=succeeded，部分成功=partial，全取消=cancelled，否则 failed。每个 run 结束时幂等重算，轻微竞态可接受。

## 多轮回看与血缘呈现

- **对话栏即轮次时间轴**：`GET /api/conversations/{id}` 返回按时间正序的 `batches[]`，前端将除最新一轮外的批次映射为 `pastRounds`，最新一轮作为当前轮。点击任意一轮的回复气泡，右侧结果区即切换到该轮的节点集合（通过嵌套独立的 `WorkspaceProvider` 隔离各轮状态，历史轮次关闭"新完成"未读红点）。
- **三种来源标识**：通过批次的 `base_page_id` 在全量批次节点中反查父节点所在的轮次与模型：
  1. 首轮（`roundIndex === 0`）：标「新建」。
  2. 指定了 `base_page_id`：标「基于 {模型名}」（若跨轮分支，如第 3 轮基于第 1 轮的结果，则标「基于第1轮 {模型名}」）；同时在被选作基点的那一轮明细表对应模型行上标「→第N轮」，形成双向血缘呼应。
  3. 未指定 `base_page_id`（`kind=continue`）：后端让各模型从最近一轮接着改（见下文「分叉」里的并行续写规则），前端标「各自续改」。
- **恢复历史时不预填待续改基点**：打开历史会话时，只用 `base_page_id` 渲染每一轮气泡上的来源标签，**不要**自动把最新一轮的 `base_page_id` 塞进输入框的待续改状态（`continueBase`），否则用户接着发下一轮时会在不知情的情况下又从旧节点分支。
- **选基点不清空草稿**：点「以此结果继续」或改选另一个结果，只更新 `continueBase`，并把焦点放回输入框，**不要** `setPrompt("")`。用户经常先写好修改说明再去选基础，清空等于丢掉这段草稿。清空只留给「草稿已经被用掉或被放弃」的动作：发送成功、新建对话、打开另一条历史会话。取消基点只清 `continueBase`。
- **节点用时持久化**：`ConversationNode` 由服务端根据 `GenerationTask.finished_at - started_at` 计算 `duration_ms` 下发，保证刷新或跨设备回看历史轮次时仍能展示准确的生成耗时与「最快」标签。

## 多轮续写的上下文策略（带哪些历史）

续写本质是"在上一版产物上改"。对"生成完整 HTML"这类产品，产物本身是完整快照，所以上下文按"指令全带、答案只带最近一版"组织最划算：

- system：通用 HTML 规则（不变）。
- user：历次"指令"清单（首轮原始需求 + 每一轮续写指令，按时间正序）。指令短、便宜，完整保留用户意图，避免"只看 HTML 推不出的约束"丢失。
- assistant：只放最近一版完整 HTML。每版 HTML 都是完整文档，已包含此前全部改动，更早版本是冗余的，多带只会撑爆上下文。
- user：本轮新指令（追加一句"未提到的部分尽量保持不变"，抑制整页重写时的无意漂移）。

并行续写时，每个模型沿"自己那条链"向上收集指令与取自己上一版 HTML（parent_page_id 天然区分链路），互不串味；中途换进来的模型则以最近一轮某个结果为父，继承那条链的指令和 HTML。

"回到更早版本"不靠上下文记忆，而靠生成树——从任意旧节点点「以此结果继续」分支即可（会分出一条新会话，见上文「分叉」），比让模型记历史更可靠。

注意：单次输出受 `max_tokens` 限制（如 8192），复杂页面可能被截断；续写时会把"上一版（可能被截断的）HTML"作为上下文，模型需重建完整页面。页面偏复杂时应调高对应模型 `params.max_tokens`。

## 扩展性与注意点

- 已升级为"批次多路复用 SSE"（一条连接合并多 run，事件带 `task_id`），并开了 HTTP/2；N 路 `EventSource` 的 6 连接限制不再是问题。
- 接请求的进程和跑生成的进程都可以多开：派发和停止用数据库通知（见 `wiki/sse-background-job-streaming.md` 第 2.5 节）；名额直接数库里在跑的任务、任务带归属与续期、超时才被接手、退出前排空（第 2.6 节）。同一批的几个模型可能分在不同 worker 上，共用的资料解析也要跨进程只做一次。
- 模型可选集合来自"模型目录 + 多选"，加模型只改配置；并行数量从 2 扩到更多无需改结构。
- 续写只需新建一个 `base_page_id` 指向某节点的批次；从更早一轮分叉则新建一条带分叉指针的会话；合并只需新建带 `source_page_ids` 的新会话根。
