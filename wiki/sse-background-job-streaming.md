# 长任务后台执行 + SSE 可续传进度

适用于「提交后要跑几分钟、过程要实时展示」的任务：LLM 生成、批量处理、导出等。核心是把**执行**和**观看**分开：任务在服务端后台跑完，浏览器只订阅事件；连接断了、页面关了，任务照常跑，回来时补齐进度。

## 一、执行不能挂在请求上

反例：第一次打开事件流时才开始调用模型，生成器直接把结果推给这个请求。

- 浏览器一断（切页面、刷新、新开对话、网络抖动），框架取消请求协程，模型调用跟着被取消。
- 取消处理里的数据库提交本身也会被取消打断，状态写不进去，任务永远停在 `running`。之后再打开只能回放旧事件。

正确做法：提交接口建好任务后立刻交给后台执行器（进程内 `asyncio.Task` 或独立队列），事件流接口只读。

## 二、后台执行器要点

- **原子认领**：`UPDATE ... SET status='running' WHERE id=? AND status='pending' RETURNING id`，没认领到就不跑，防止重复执行。
- **并发上限分两层**：只有全局上限时，一个用户一次提交几十个任务（或重启后批量重跑）就能占满名额，后来的用户只能等。先过「个人上限」再过「全局上限」：个人名额没轮到的任务不去排全局队，挤不到别人。个人上限从「用户单独设置 → 套餐 → 默认值」一处取，会员放宽只改这里。
- **名额闸门要能调上限、按提交顺序**：`asyncio.Semaphore` 容量固定，用户升级后放不宽，自己写一个先来后到的闸门（计数 + future 队列，调大上限时立刻唤醒排队的）。入队必须是协程第一步的同步调用，前面不能有 await，否则同一用户的任务会乱序。
- **排队凭证要能作废**：拿到排号后、真正等待前还要写一条「排队中」事件（有 await）。这期间被停止或出错，排号还在队里，轮到时名额被占却没人用，名额就永久少一个。把「入队 → 写事件 → 等待」包在一个函数里，异常时统一处理：还没轮到就取消排号，已经分到就还回去。写排队事件失败只记日志，不能让任务因此卡在排队里。
- **排队要让用户看见**：排队时写 `queued` 事件（带原因），轮到时写 `started`，库里任务保持 `pending`。前端单独显示「排队中」，排队时间不计入生成用时；刷新后 `pending` 直接还原为排队中。
- **兜底写终态**：执行协程的 `finally` 里检查任务是否到了终态，没有就用**新的数据库会话**补写（原会话可能正处在被取消或出错的事务里），用 `asyncio.shield` 包住。
- **开跑前被取消不会走 finally**：`Task.cancel()` 发生在协程第一次运行前时，协程体根本不执行。登记表清理要放在 `add_done_callback` 里，排队中被停的任务要由调用方自己写成 `cancelled`。
- **停止分两步**：先设标志，在两个数据块之间检查并抛专用异常，走正常收尾；宽限几秒还没退出（外部服务卡住不吐数据）再 `task.cancel()`，由兜底写库。注意专用异常不能被「失败就重试」的 `except Exception` 吞掉，要先单独 `raise`。
- **进程退出不改状态**：关闭时只取消协程，把未完成任务留给下次启动扫尾。这样被 SIGKILL 和正常退出走同一条恢复路径。
- **启动扫尾**：按「最近活动时间」（最后一条事件、开始时间、创建时间取最晚）分流：近期中断且没自动重跑过的从头重跑一次，并写一条 `restarted` 事件让前端清空旧进度；没开始过的直接排队；其余标失败。重跑次数要有上限，否则每次重启都会重来。
- **多进程**：进程内登记表和名额闸门只适合一个进程跑任务。想多开接请求的进程、又不想引入外部队列时，见下一节；执行进程也要多开时，见 2.6 节（名额入库、任务续期、排空）。共用线上库的预览实例要关掉扫尾，否则一启动就去动线上任务。

## 2.5 接请求的进程多开、执行进程只开一个（数据库通知）

把进程分成两种：web 只接请求、推事件流，可以开多个、逐个重启；worker 只有一个，持有登记表和名额。两边用 PostgreSQL 的 `LISTEN/NOTIFY` 传三件事：派发新任务（web 到 worker）、停止任务（web 到 worker）、任务有新事件（worker 到所有 web）。不需要 Redis。

- **通知只是提速，正确性靠库里的状态。** 通知在提交时送达，监听连接断开期间的通知直接丢失。所以 worker 要定时扫一遍没人领的 `pending` 任务和带停止标记的任务；web 在监听连接不健康时，事件流改为每隔一两秒读库。
- **发通知走连接池的普通会话，在数据已经提交之后（或同一个事务里）发。** 先发后提交，worker 可能读不到任务，只能等下一轮扫描。也不要依赖发送方自己的监听连接，它坏了通知就发不出去。
- **监听要用专用连接，并定期探活。** 连接池里的连接会被归还、复用，挂不住 `LISTEN`。TCP 被中途掐断时，连接对象看着还在，却再也收不到通知；每隔一段时间 `SELECT 1` 并设超时，失败就断开重连。重连后要把可能漏掉的状态补读一遍：worker 立刻扫一次，web 唤醒所有挂着的事件流。**断开的那一刻也要唤醒一次**：已经在按心跳间隔（如 15 秒）等通知的事件流，不唤醒就要等满这一轮才发现该改成定时读库。
- **合并只做一次。** 发送方已经把一小段时间内的批次通知合成一条时，接收方被唤醒后就不要再等一会儿攒事件，两次各 200 毫秒会叠成 400 毫秒的延迟。
- **（只用于内存名额闸门；名额入库后排队任务不再占协程，见 2.6）排队中的任务被别的进程直接写成终态、通知又丢了**，worker 内存里还挂着它的排队协程。定时扫描除了找带停止标记的在跑任务，也要对照一下本进程还没认领的任务在库里是否已经结束，结束了就丢掉协程。
- **停止要在行锁里看当前状态，只让一方写终态。** web 不知道任务在 worker 里跑到哪一步。加锁后还是 `pending` 的由 web 直接写成已停止；已是 `running` 的只打停止标记、通知 worker，由 worker 写终态。照搬单进程里「不在本进程跑就直接写终态」的做法，会和正在跑的 worker 抢着写，状态被改回、结算两次。
- **web 自己写了终态，要自己发「有新事件」的通知。** worker 不会为它没跑的任务发通知，挂在另一个 web 实例上的事件流就要等到下一次心跳才知道。
- **worker 收到停止时，任务可能刚在库里认领成功、还没在内存里登记。** 这时直接取消协程，会留下一条永远停在 `running` 的任务。先查库：已是终态才直接取消；否则只设停止标志，等认领登记后按停止收尾。
- **扫尾要认停止标记。** 用户点了停止、worker 还没停就退出了，重启后要写成已停止，不能按「近期中断」重跑。
- **预览实例不能开 worker 的定时扫描。** 它会把共用库里的 `pending` 任务领走。
- **滚动重启 web 时，要等前一个实例恢复、再等过反向代理的失败冷却时间，才动下一个。** nginx 在 `fail_timeout` 内仍把刚恢复的实例当作不可用，连着重启会出现两个实例同时不可用的空档。
- **配置文件缓存要能跨进程失效。** 管理接口改了配置文件、只清了处理请求那个进程的缓存，其他进程会一直用旧值。按文件修改时间每隔几秒检查一次。

## 2.6 执行进程也多开：名额入库、任务续期、退出前排空

上一节的 worker 只能开一个，因为名额和登记表在它内存里；发版重启它会打断在途任务。不加 Redis 也能多开，星页 2026-11-13 这样做（代码 `generation_runner.py`、`app/worker.py`）：

- **名额不另存计数，直接数库里 `running` 的行。** 计数器要靠进程退出时归还，进程被强杀就漏。认领在一个事务里：先 `pg_advisory_xact_lock(固定键)` 让所有 worker 排着来，再数全站和每人在跑的数量、按先后挑 `pending` 任务、`UPDATE … WHERE status='pending' AND cancel_requested_at IS NULL RETURNING id`。锁随事务提交释放。给 `status='pending'` 和 `status='running'` 各建一个部分索引，两类行都很少，数起来很便宜。
- **同一事务里插入的行 `now()` 都一样。** 按 `created_at` 排先后时会按 id（随机 UUID）打乱，同一批的任务开始顺序随机。插入时按顺序错开 1 微秒。
- **排队事件每种原因只写一次。** 每轮认领都会重新判断一遍谁在排队，不去重会每秒写一行。
- **空出名额要叫醒所有 worker。** 本进程任务结束时，自己马上补领一轮，再发一条派发通知让别的 worker 也补领（同一时刻的多次合成一条）。
- **任务记归属和续期时间。** 认领时写 `worker_id`、`heartbeat_at`，每 10 秒续一次。接手只看续期超时（45 秒）的；判断用 `coalesce(heartbeat_at, started_at, created_at)`，兼容升级前没有续期的老行。启动扫尾也只能动续期过期的，否则一个 worker 重启就会把别的在线 worker 的任务重跑一遍。
- **续期时发现任务不归自己了，停掉本地协程、不写库。** 进程卡顿超过 45 秒会被接手；回过神来如果照常写终态，就和新的执行者抢写。续期 `UPDATE … WHERE worker_id=本进程 RETURNING id`，没返回的再查一下：已是终态说明是自己正在收尾，不算被接手。认领时也要跳过本进程登记表里还有的任务（被接手退回 `pending`、但本地旧协程还没停）。
- **光靠续期发现不够，写终态前还要在行锁下确认归属。** 续期是定时的，旧执行者可能在两次续期之间跑完，直接把新执行者手上的任务写成成功：多出一个版本、多结一次账。做法：写终态的事务里先 `SELECT status, worker_id … FOR UPDATE`，仍是「在跑且归自己」才写，否则回滚整个事务。行锁持有到提交，接手方的重置要等它，两边不会交错。接手一方也一样：查出过期任务后，重置前在行锁下再判断一次是否仍然过期。共用前置步骤（资料解析）的结果写回同理；被接手时只清理自己独有的产物，按固定键写的产物（接手方会写同一个键）不能删。先写复现测试再修：让旧执行者卡在模型输出前，把续期改旧，另一个执行者接手，再放旧的跑完。
- **扫尾要互斥，但锁不能放在扫尾的事务里。** 扫尾过程中要多次提交（逐个写终态、重算批次），`pg_try_advisory_xact_lock` 在第一次提交时就释放了。另开一个会话，在它的事务里拿锁，扫尾做完再提交这个会话。拿不到锁就跳过这一轮。
- **停止通知可能比登记先到。** 停止通知广播给所有 worker，不是自己手上的任务时记下来（60 秒过期）；本进程刚在库里认领、还没登记的任务，登记时补上停止标志。
- **退出前排空。** 收到 SIGTERM 后不再认领，续期和停止照常处理，等手上的任务跑完再退出；systemd 的 `TimeoutStopSec` 要比排空时限长。超时（或排空时再收到一次信号）才取消剩下的协程，并把它们的 `heartbeat_at` 写成很早的时间，别的 worker 下一次扫描就接手，不用等 45 秒。滚动重启脚本一个一个来：前一个起来了再停下一个，任何时候都有 worker 在领任务。
- **几个任务共用的前置步骤（例如同批的资料解析）也要跨进程只做一次。** 用同样的原子更新抢：状态是待做，或在做但续期过期的才抢得到；抢到的定时续期，没抢到的每秒查一次结果。进程退出时交出（清空续期、不删原件），只有用户停止才记失败。
- **新老版本不能同时在线。** 老 worker 不续期，新 worker 会把它跑了 45 秒以上的任务当成失联接手重跑。切换时先停老的、确认没有在途任务，再启新的。
- **测试库里的遗留任务会被认领。** 按库认领会捡起测试库里所有 `pending` 任务，别的用例留下的（模型 key 是假的）会被跑起来、卡住。每个用例前后把未结束的任务收掉。

线上实测（4 核单机，2 个 worker）：两个任务分到两个 worker，0.03 秒内开始；滚动重启两个 worker 时各自等手上的任务跑完（10 秒、17 秒）才退出，两个任务都没被打断；生成中 `SIGKILL` 一个 worker，45 秒后另一个接手、从头重跑一次并完成。

## 三、事件流可续传的坑

- **全局自增序号 ≠ 提交顺序**。多个任务并发写同一张事件表时，A 先拿到 100 号、晚提交，B 拿到 101 号先提交；只用一个全局游标「读 > last」会永久漏掉 100。同一个任务里，一次提交可以有多行，行的写入顺序就是序号顺序，所以**每个任务各维护一个游标**，查询写成 `(task_id = A AND seq > ca) OR (task_id = B AND seq > cb) ...`。`(task_id, seq)` 上有唯一约束就够了，再加一条同样列的普通索引只是让每次写入多维护一份。续传 id 可以是按固定顺序拼起来的各任务游标字符串，SSE 的 id 不限于数字。
- **终态和收尾事件同一个事务提交**。否则订阅方会看到「状态已结束」但收尾事件还没写，要么提前结束漏掉 `completed`，要么一直等。同事务后，「终态但没有收尾事件」只可能是旧数据，可以按状态补一条。
- **续传要先补「已结束」集合**。客户端带着游标重连时，游标之前已经收到过收尾事件的任务不会再出现，要先查出来，否则会一直等它们结束。
- **合并碎片事件**：回放时把同一任务连续的增量文本合成一条，大幅减少事件数；合并只在任务内进行，跨任务顺序可以变。id 只放在每块的最后一条，块中间断开会从上一块末尾重发，宁可重复不可遗漏。
- **唤醒要先取 waiter 再读库**：用 `asyncio.Event` 做通知时，订阅方先拿到当前 Event，再查数据库，再等待；否则「查完之后、等待之前」到来的通知会丢，只能等超时。唤醒后稍等（如 0.2 秒）合批再读，避免每条事件都查一次库。
- **心跳**：空闲时定期发 `: ping` 注释行，避免反向代理读超时切断连接。

## 四、流式输出不要逐片落库

一个思考模型一次生成大约三千个碎片、每片几个字。每片一次插入并提交，几百个任务就会把事件表写成几十万行。连接池吃紧是因为提交太密，不是因为等模型吐字时占着连接：常见的数据库会话在提交之后就把连接还回池。

先看界面到底用不用这些碎片。思考文本如果只是放进状态、没有组件渲染，把合并间隔拉长不影响打字效果。进度如果同一阶段后来的覆盖先前的，中间几十条 token 计数也可以收成最后一条。完成时带真实用量的那条要单独留下。

- **按任务在进程里缓冲。** 第一段马上落库，界面常靠「有没有第一段」切换状态（例如切到思考中）。之后按时间或字数再写。只在收到新碎片时检查即可；界面在卡住时也要看到「还在想」，才需要定时器。
- **其它事件落库前，先把缓冲放进同一个事务、排在前面。** 重试前通常会先写一条状态，缓冲就跟着写出去，不会丢。任务内顺序也不变。
- **硬取消不要刷缓冲。** 协程被取消时，原会话可能停在半次提交里。用新会话写终态。丢掉的是没人看的尾部。
- **不要把越来越长的全文反复更新到任务行上。** 数据库每次更新都会重写这一列，写入量随长度上涨。追加新行，或合并后再插入。
- **删索引要连最初的建索引语句一起删。** 有的迁移会按文件名重跑全部 SQL。只加一条 `DROP INDEX`，下次迁移会先把索引建回来再删掉。
- **历史数据可以事后合并，但只动已经结束、并且结束超过一段时间的任务**，避免和还在读的订阅抢。连续的增量文本按序拼接；同一阶段、同一状态的进度只留最后一条。序号留在这段的最后一行：游标已经走过中间号的客户端会再收到合并后的全文（多发），不会漏掉后面的内容。
- **按主键分批删除。** 有的驱动一条语句最多三万多个参数，一个超长任务一次塞进去会整段失败。每个任务一个事务：失败的那个回滚，前面已经提交的是完整的。
- **合并后做普通 VACUUM，不要顺手 FULL。** `VACUUM (ANALYZE)` 清掉死元组、更新统计，读写还能继续，但不会把磁盘还给系统。`VACUUM FULL` 才还空间，并且会锁表，另选窗口。

测试里把间隔调小，才能让「取消前至少写出几行」在超时内通过；把间隔调大，才能断言「几百片只落一两行」。改的是进程里缓存的那份配置，用例结束时要还原，否则后面的用例会沿用被改过的间隔。

## 五、浏览器与代理的坑

- **EventSource 遇到非 200 会永久关闭**。网络断开时它会自动重连并带 `Last-Event-ID`；但重连时如果拿到 502（后端重启期间）或 401，`readyState` 变成 `CLOSED`，不再重试。需要在 `onerror` 里判断 `CLOSED`，自己按退避重连，用查询参数带上最后的游标（原生 EventSource 不能自定义请求头）。用户离开页面时要作废待执行的重连。
- **中间层压缩会把实时事件攒住**。Next.js 开发服务器的 rewrite 代理会对 `text/event-stream` 做 gzip，小块事件堆在压缩缓冲里不发，只有一大块回放能冲出来。SSE 响应头加 `Cache-Control: no-cache, no-transform`。nginx 默认 `gzip_types` 只含 `text/html`，不会压缩事件流；同时要 `proxy_buffering off`。
- **开发代理不一定在上游断开时关闭下游连接**，测不出重连逻辑。验证断线重连要走和线上一样的 nginx。
- **HTTP/1.1 同源 6 条连接**：多个并行任务各开一条 EventSource 会排队，同域 iframe 也占名额。合并成一条流，并开 HTTP/2（nginx 1.24 写 `listen 443 ssl http2`，1.25.1 起用 `http2 on`）。
- **uvicorn 优雅退出会等 SSE 连接关闭**，所以 systemd 要设较短的 `TimeoutStopSec`。强杀不影响正确性，前提是第二节的「退出不改状态 + 启动扫尾」。

## 六、验证清单

1. 生成中切走、新建对话，确认库里事件仍在增长。
2. 回到会话，确认回放后继续实时更新。
3. 生成中重启后端，确认前端自动重连、任务被重跑且前端清空旧进度；再重启一次，确认超过重跑次数的任务被标失败。
4. 点停止：已完成的保留并计费。未过起扣线的显示「已停止」并退回预留；超过起扣线的主动停止按成本保底收费，界面仍只显示「已停止」。
5. 刷新后从历史打开，停止和失败状态都能从服务端正确还原。
6. 连吐几百段思考，确认落库远少于碎片数，且最后一段思考的序号早于「开始输出正文」。完成后的进度仍带真实用量。
