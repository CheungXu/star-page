# 上传资料辅助生成页面的处理原则

用户上传文档、图片来辅助生成页面时，把流程拆成三段：**创建时只预检 → 后台解析一次、全批共用 → 每轮由写码同款模型按需求提取**。图片分「让模型看到」和「让页面用上」两个通道。本仓库的实现见 `code/backend/app/services/document_parser/README.md`。

## 1. 创建请求只做便宜的检查

- 创建接口里只做预检：文件头与扩展名是否一致、能否打开、是否加密、页数、Office zip 解压后的总大小和条目数、图片像素。不合格直接 4xx，不建任务、不扣免费次数。
- 完整解析放到后台。解析可能很慢（大 PDF、渲染快照），放在创建请求里会被网关超时掐断。
- 上限要严格且前后端一致。当前：最多 3 个文件，单文件和总计 50MB，图片 10MB，PDF 30 页，PPTX 40 页，DOCX 2000 段，每个文档最多取 20 张图，单文件解析 60 秒超时，zip 解压不超过 150MB，图片不超过约 6000×6000 像素。
- Nginx 的 `client_max_body_size` 要略高于业务上限（当前 60m）。

## 2. 后台解析：一次解析，全批共用

- 多个模型并行生成同一轮时，解析只做一次。解析要做成**批次级的独立任务**，不能挂在某个模型的协程上：用户停掉那个模型、执行器硬取消它的协程时，其他模型等的解析也会跟着断。各模型只「等结果」。「正在等的人都走了」不等于「没人要了」：有并发上限时，同批还有模型在排队、还没走到解析这一步，这时取消解析会让它们一上来就失败。所以只有同批已经没有排队或在跑的任务时才取消；判断时要排除刚被停掉、终态还没写进库的那几个。解析任务的登记要保留到解析真正结束，否则后到的模型会再拉起一份解析。
- 放进线程的解析超时后停不下来，只能不再等它。所以单个文件的工作量要靠上限兜住。
- 原件只在解析期间存在：成功、失败、取消、创建失败（如余额不足返回 402）都要删。进程重启时把「解析中」退回「待解析」；批次里已经没有任务要跑的，删掉暂存原件。

### 各格式的要点

- **PDF**：按字符坐标找页面中段的竖向空隙判断双栏，先左栏后右栏；跨栏的标题行单独成段。注意中文无空格排版一整行往往只是一个「词」，直方图必须**按「行」去重统计**而不能按「词」统计（否则行数较少的中文双栏页样本不足会漏判），并容忍约 15% 的跨栏标题/导语穿过中线，防止顶部两三行大标题把双栏中缝“堵死”。页眉页脚按「页面上下 8% 区域里、半数以上页面重复出现的行」去掉。
- **少字大图页 / 扫描件**：每页统计有效字数。字很少、又有大图或大量矢量图形的页，或整份文件几乎没有文字层的，渲染成整页快照给模型看。扫描底图（占页面七成以上）不要当配图取出来公开。
- **PPTX**：组合形状要递归展开，否则组里的文字会漏；同一形状树的顺序不等于阅读顺序，按（纵向分桶，横向位置）排序。图表取出类别和数值，备注和母版主题色也有用。
- **DOCX**：段落和表格按正文原顺序遍历；浮动图和文本框不在普通段落流里，要单独扫。Word 会给文本框写一份 VML 兜底，只取主版本，否则内容重复。有合并单元格的表格转成 HTML（保留 rowspan / colspan），转 Markdown 会错位。
- **Excel**：小表整表给出；大表不要交给模型「压缩」，模型摘要会改数字。由代码算统计画像（行列数、数值列合计/均值/中位数/极值、分类列 Top 分布），再附首尾样本行。合并表头先把值铺满合并区域。预检阶段对 `.xls` / `.xlsx` 除了校验容器头，还应只读试打开工作表目录，在创建请求里直接拦住损坏或加密的工作簿。
- **许可证**：PyMuPDF / pymupdf4llm 是 AGPL，用在对外服务的后端上需要公开源码或购买商业授权。宽松许可的组合：pdfplumber（MIT）+ pypdfium2（BSD/Apache），python-pptx、python-docx、python-calamine 都是 MIT。

## 3. 每轮同模型提取，替代「长文压缩」

- 压缩只在首轮做一次，到了续写轮次，模型就再也看不到原文了。改成**每一轮**都用「全部资料原文 + 历次需求 + 本轮需求」重新提取本轮用得上的内容。
- 用写码同款模型提取，但**关闭思考**，否则长文档提取会拖到几分钟。各厂商关闭思考的写法不同，必须实测（见下文）。
- 本轮需求和资料无关（只改配色、间距）时，让模型输出一个约定标记（如 `<EMPTY/>`），这一轮不往写码模型里塞资料。要和「调用成功但正文为空」区分开：后者应该重试。另外，「没有正文、只点名了图片」不算无关：扫描件续写时提取模型没字可摘，只能指出要看哪张快照。
- 提取阶段只喂文字，不附图。图片以**锚点文字**出现在原文里（ID、位置、尺寸、是不是少字页的核心大图），模型用一行 `IMAGE_REFS: id1, id2` 指出本轮写码要看或要用的图。
- 资料除锚点外几乎没有文字时（扫描件、纯图 PPT），纯文本提取等于空转，容易误判成「无关」。在它上传的那一轮跳过提取，直接把图交给写码模型。统计有效字数时，页码标记、文件头这类结构行也要去掉。
- 跨轮收集资料要和会话详情接口同一口径（含分叉继承），同一个文件多轮重复上传时按原始字节哈希去重；总长设上限，超了优先保留本轮的资料。
- 提取用量并入该模型这次生成的用量一起计费。

## 4. 图片双通道

- **让页面用上**：图片存成平台托管资源，在消息里列出地址。用户上传的、场景槽位的图写明「必须使用」；文档配图标明位置和尺寸，模型按需选用。同一批次多份文档包含相同图片（如共用公司 Logo）时，存储层按哈希只存一份，但每份文档正文原位置都要复用同一个资源 ID 写出锚点，不要把后续文档的占位符直接抹空。整页快照从不列地址。
- **宽高方向与 Pillow 校验坑**：手机竖拍 JPEG 常以「横向像素 + EXIF Orientation 旋转 90°」存储，读取宽高写入数据库/Prompt 前必须按 EXIF 方向换算成真实显示宽高，否则模型会把竖图当横图排版；同时 Pillow 的 `Image.verify()` 必须在 `Image.open()` 后立即调用（先调 `getexif()` 再调 `verify()` 会抛 `RuntimeError`），读 EXIF 与做完整性校验应分两次打开。
- **让模型看到**：能读图的模型收到缩小后的原图（长边 1536px 以内，最多 6 张）。只在本轮新上传了图片、或提取结果点名了某些资料图片时才附；续写轮次不重复附历史图片，上一版页面里已经有引用。
- 托管资源地址是公开的（只是不可猜），整页快照可能是扫描的证件、简历，只存私有键，不进公开资源表。会话支持分叉继承时，软删除子分叉可能连带释放早已软删的来源父会话节点，清理私有快照要扫描该用户名下所有已软删且无存活节点的批次，避免父会话快照残留。
- 不能读图的模型：适配层丢掉图片，只发文字和地址，进度里提示一句。带图请求在吐字前返回 400 时，去掉图片再试一次（有的模型带图直接报错，有的会静默忽略）。
- 数据库和调试记录里只记图片的说明和资源 ID，不存 base64。

## 5. 模型能力要实测

读图能力和关闭思考的写法都不能照文档猜，用探测脚本实测后写进模型目录（`supports_vision`、`extraction_extra_body`）。2026-11 的实测结论：

- 读图：用纯色图问颜色。有的模型带图直接 400（GLM-5.3），有的不报错但回答错（DeepSeek V4 Pro 把红色答成白色），两种都算不支持。
- 关闭思考：要看思考量是否归零，不能只看是否报错。方舟会接受 `enable_thinking: false`，但仍思考几十个 token，要用它自己的 `thinking: {type: disabled}`；GLM-5.3 不允许关，只能 `reasoning_effort: low`。

## 6. 调试信息

任务记录里存：用户原始需求、上传文件名、带锚点的抽取原文、本轮提取结果（空串表示无关）、提取 prompt 说明、最终发给写码模型的文字（附图只记说明）、模型原始输出、生成 HTML 的存储位置。这些只给管理员看。

## 7. 进度节点

```text
上传文件（如有） -> 解析文件（本轮有文档） -> 提取关键信息（会话里有文档） -> 模型思考 -> 模型输出答案 -> 部署
```

续写轮次没传新文件，但会话前面传过文档时，也要显示「提取关键信息」。前端可以从历史轮次的进度里有没有这个节点推出来，分叉时只看分叉点及之前的轮次。

## LLM 重试原则

- 底层客户端统一重试可恢复错误：网络失败、超时、协议中断、JSON 解析失败、`429` 和 `5xx`。
- 提取不需要流式展示，用「收集完整正文」的调用方式并要求正文非空。
- 页面生成要流式展示，只能在正式 HTML 开始输出前重试；开始输出后再重试容易重复或拼接损坏。
- 重试次数、初始退避和最大退避都要可配置。
