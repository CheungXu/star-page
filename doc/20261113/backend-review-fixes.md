# 后端拆分后的复查与修补

日期：2026-11-13。凌晨 03:43 上线，接请求的两份轮流重启，跑生成的那份在没有在途任务时重启。

## 为什么做

11-12 把后端拆成「两份接请求 + 一份跑生成」后，对照拆分前列出的几个单进程问题逐条复查，看哪些真正解决了、哪些只解决了一半，并把复查中发现的实现瑕疵补上。

## 复查结论

| 拆分前的问题 | 现在 |
| --- | --- |
| 生成状态只在一个进程里，多开进程互相看不见 | 已解决。接请求的可以开多份，生成集中在一份里 |
| 一次大计算卡住所有人 | 大部分解决。生成收尾的页面处理在另一份进程里，不再影响网页；分享页和分享图的处理不再卡住同进程的其他请求。打开分享页时的整页处理仍只能用一个核，见下文「还没解决的」 |
| 4 核只用上 1 核 | 已解决。现在是 3 个后端进程加前端 |
| 后台线程只有 8 个，慢的挤占快的 | 本次修好。每个进程放大到 32 个；文件解析单独 3 个，慢文件不再挤占别的任务 |
| 发版打断在途生成 | 改接口时已不打断。改生成本身仍要重启跑生成的那份，见下文 |
| 单进程连接数上限 | 本次修好。原来每个进程最多 1024 个连接，已放开到 65536 |

## 本次修了什么

1. **读取存储里的页面时，有一半工作还在卡主流程。** 打开分享页、图片时，从存储下载正文这一步没放进后台线程。已改到后台线程，并让同一进程复用到存储的连接，不再每次重新握手。线上同一页面连续打开三次，第一次 0.14 秒，之后 0.10、0.05 秒（复用了连接）。
2. **后台线程不够用。** 见上表。
3. **连接数上限过低。** 见上表，三个后端进程都已确认生效。
4. **提交生成成功、却可能报错。** 生成已经记下、积分已经冻结之后，再通知跑生成那份的这一步如果碰上网络抖动，会给用户报错，用户重试就会重复提交。现在这一步失败不报错，跑生成的那份 5 秒内会自己发现这批任务。
5. **进度通知断线时，页面最长 15 秒没动静。** 两部分之间的通知连接断开的那一刻，正在等进度的页面要等满一轮 15 秒才改为自己查库。现在断开时立即切换。
6. **进度多等了 0.2 秒。** 发送和接收两边各攒 0.2 秒，叠成 0.4 秒。接请求的那份不再重复等待。
7. **排队中被停掉的任务，通知丢了时还占着位置。** 现在跑生成的那份每 5 秒检查时会顺手清掉。
8. **按访问来源限制的匿名免费次数、短信次数可以被绕过**（11-12 记录的遗留问题）。后端原来读的是访客自己能填写的那段来源信息，现在只读网站入口写入的真实来源。线上验证：伪造来源的请求照样被拦下。
9. **同一网络当天新建匿名身份超限时，用户看到「服务器错误」**（11-12 记录的遗留问题）。现在任何页面都统一提示「请登录后继续」。线上已验证。

上次复查里有一条判断经实测不成立：以为重启接请求的那份时，挂着的进度连接会拖住退出。实测当前版本 0.2 秒就能退出，不需要改。

## 还没解决的，以及怎么解决

按建议的先后顺序：

1. **热门分享页被大量打开时，整页处理只能用一个核。** 每次打开都要从存储下载整页、再改写页面头部的分享信息，这一步在一个进程里只能用一个核。
   - 建议先做：把改写好的页面按「页面版本 + 分享标题」在内存里缓存一份。页面版本生成后就不会变，缓存不会过期出错；下架、删除照常每次查库判断。爆款页面被反复打开时，第二次起不用下载也不用处理。约 1 天。
   - 再做：分享信息不再整页解析，直接在页面头部插入，处理快一个数量级。约半天。
   - 流量更大时：分享页走 CDN 短时间缓存，下架或删除时主动清缓存。
2. **改生成本身时，重启仍会打断在途生成并重跑。**
   - 建议先做「排空后再退出」：收到重启信号后不再领新任务，等手上的任务跑完（最多等几分钟）再退出；新提交的任务在库里等着，新进程起来后接着跑。用户感受是重启期间新任务晚开始几分钟，不再白跑、不再重复付模型费用。约 1 天。
   - 如果要做到完全无感：把「每人最多 10 个、全站最多 48 个」的排队名额从进程内存搬进数据库，新旧两个跑生成的进程就可以同时在线，旧的排空、新的接手。这一步做完，两台机器一起跑生成也就具备条件，仍不需要新增服务。约 3 天。
   - 需要多机且生成量很大时，再按 `alternatives/backend-process-model/README.md` 的方案二引入消息队列。
3. **接请求的进程忙不过来时**：直接多开一份（例如第三份），网站入口配置加一行即可。这台 4 核机器上最多开到 3 份。
4. **缺少监控**：目前不知道主流程有没有被卡、后台线程有没有排队。建议加一个每分钟一行的日志：主流程延迟、线程排队数、在跑生成数，出问题时能直接看到是哪里。约半天。
