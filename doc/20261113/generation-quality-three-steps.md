# 生成质量三步升级：截断自动续写、续写局部修改与发布前渲染自检

日期：2026-11-13。上午 09:42～09:45 分三次滚动上线，网站与在途生成零中断。

## 背景与痛点

此前星页每个模型生成页面都是「单次一竿子到底」输出完整页面，随着复杂交互页、长报告页和多轮微调场景增多，暴露出三个影响交付体验的质量短板：

1. **长页面写到一半被截断**：模型因输出长度上限或中途截断没写完，页面缺少下半部分甚至连样式/脚本都没闭合，直接发布了残缺页面。
2. **多轮微调耗时久、易改丢细节**：用户只想「改一句标题」或「换个按钮颜色」，模型也要把几百行代码从头重写一遍，不仅等待一两分钟、多花不少积分，还偶发把上一版没提过的段落悄悄改掉。
3. **代码语法过了但打开报错或白屏**：生成页允许交互脚本和动效后，偶发出现脚本运行报错、违反页面安全沙箱限制（如读写浏览器本地存储）、或入场动画卡在全透明导致首屏白屏，系统此前无法感知。

## 三步改造方案

围绕已确认的产品与计费原则落地三道保障：

1. **第 1 步：输出截断检测与断点续写**
   - 自动识别模型是否因长度限制没写完；一旦截断，进度提示「输出被截断，正在续写」，让模型接着断点补齐下半部分并无缝拼合。
   - 若补写一次后仍然写不完，不再把残缺半页发给用户，而是明确提示「页面内容过长，未能完整生成」，并**全额退回预冻结积分**。
2. **第 2 步：多轮续写优先局部修改 + 整页兜底**
   - 从第二轮修改起，允许模型自主二选一：小中幅改动只输出需要替换的局部片段（未提及区域原封不动保留，速度大幅提升）；大幅改版则输出完整新页面。
   - 任何一处替换片段若与上一版原文对不上，整次局部替换自动作废，无缝回退为让模型输出完整页面，保证绝不拼坏页面。
3. **第 3 步：发布前无头浏览器自检与一次自动修复**
   - 页面生成后、正式发布前，在后台沙箱浏览器里真实打开页面跑约 3 秒，检查是否有脚本报错、首屏白屏或页面卡死。
   - **绝不阻断发布**：浏览器繁忙或超时一律跳过并照常发布；开启自动修复档后，发现问题会把具体报错位置发给模型自动修一次，修完仍有问题也**照常发布**，仅在结果卡片上温和提示「可能有显示问题」，方便用户决定是否再改一轮。
   - **计费口径**：截断续写、局部修改回退、渲染问题自动修复多出来的模型调用，均按实际总消耗正常计入用户账单（超出预冻结时走既有单任务封顶机制）；平台原有的样式规范重试仍由平台承担。

## 当前状态与后续切入「自动修复档（`repair`）」的标准

目前第 1 步（截断续写）和第 2 步（续写局部修改）已在现网**正式全量生效**；第 3 步（发布前渲染检查）处于 **`observe` 观察期**（每次生成都会在后台真实跑一遍检查并记录数据，但暂不触发自动修复、也不在前台展示问题标签，且观察期记录未来不会回溯打标）。

**观察期结束切入 `repair` 正式修复档的判断标准**（预计观察 2～3 天或累计 50～100 次新生成后评估）：

1. **误报率指标**：抽查观察期内被记为异常的生成版本，确认正常展示页（含纯图表/海报/动画页）被误判为白屏或报错的比例 **低于 2%**。
2. **性能与资源指标**：生成进程监控中渲染检查无持续排队跳过（`skipped` 占比低于 5%），单进程内存稳定在安全水位内，事件循环无明显卡顿。
3. **切换操作**：达标后只需把生成服务配置中的检查档位从 `observe` 改为 `repair`，执行一次轮流重启脚本即可平滑生效，无需改动数据库、接口或前端。

2. **续写时模型先写一句说明再重发整页**：此前两份页面会叠在一起，现在识别后只保留新页面。
3. **局部修改续写恰好在 `<html` 处断开**：此前会误判为重发整页而丢掉已输出的修改，现在照常拼接。
4. **页面已完整闭合但厂商报“达到长度上限”**：不再多续一次（续写返回空会导致整单失败）。
5. **厂商未给结束原因时的纯文字拒答**：不再误判为截断并提示“页面内容过长”，改按“未返回有效页面”失败退款。
6. **数据库提交失败后的收尾**：回滚后补充刷新任务记录，失败原因与半成品能正常写回（真实数据库实测，未刷新时收尾会再次报错）。
7. **自动修复没有改善时退回修前页面**（`repair` 档尚未开启，提前修好）：复检问题数没有减少时发布修前页面，仍打“可能有显示问题”标签；修复轮用量照常计费。

暂不处理：续写时模型重复抄写断点前末尾（暂无观测证据，自动去重有误删风险）；自动修复前后各报一次“输出完成”导致进度数字跳动（仅 `repair` 档、纯展示）。
